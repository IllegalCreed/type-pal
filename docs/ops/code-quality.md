## 目的

本页是全项目代码质量与验收的长期合同，落实用户2026-10-18对八维质量、文件组织自由、低成本独立复验和执行分工的要求。适用于新功能、缺陷修复、重构、测试和工程工具；不随代码治理专项结束而失效。第一、二阶段共用质量标准，各自的机制、架构和内容真源仍按阶段规范判断。

本页维护完整条款；[AGENTS](../../AGENTS.md#操作与必读)、[开发与验收流程](agent-workflow.md)、[任务模板](templates/README.md)引用本页。具体范围、授权、执行事实和进度由当前任务/评审记录承载，不在规范中复制治理数字。功能正确、代码质量合格和必要质量门通过共同构成完成。

## 前置条件

- 明确用户授权范围、阶段、单一Coding Owner、受影响模块和验收方式。新功能按其已批准范围改变行为和接口；专项治理的行为冻结只适用于相应任务，不扩展成全项目禁止变更。
- 从工程→模块→功能→文件理解职责、依赖和状态生命周期。完整读取受审代码，核真实生产caller、公共出口、相邻类型及资源所有权；静态引用搜索只是入口，不代替语义阅读。
- 证据区分原始数据、SDLPal参考、本项目观察和用户裁决。第一阶段必要时读[机制真值](../phase1/game-mechanics.md)；第二阶段按[READ-FIRST](../phase2/READ-FIRST.md)，不移植第一阶段代码组织或保真假设。
- 既有A维证据可按具体版本和适用范围复用。相关实现、caller、依赖、输入域或合同变化后重新判断有效性；文件哈希相同不能证明其调用环境未变。
- 历史done/partial、包级全绿、覆盖率或作者署名不自动授予本轮质量信用。只读试审按范围交付，不获得产品修改或合并权限。

## 步骤

### 1. 逐文件核清八维

每个文件分别记录八维结论、具体依据、问题及处置。结论可以是有证据支持、有具体问题、未知、N/A（具体原因）；不使用无依据的“已检查/全部良好”。“未发现”限定于已核读范围；批次级一句话不能代替各文件结论。代码审查切片缺任一维不升partial，关键未知或重要问题未解决不得关闭文件。

#### A 正确性与边界

完整读取实现；核真实caller、公共出口、相邻类型和生命周期。检查输入合法性、边界、失败传播、异步取消、资源清理、重入与状态ownership。涉及第一阶段机制时核一手真值，不能仅由实现和测试自洽得出正确；充分且有效的既有真值证据可以引用，不要求重复考据。

外部输入、路径写入、敏感信息和权限边界按实际适用范围检查；安全性不能由正常输入测试推定。明确区分已证缺陷、可改善结构和未知项，不从不一致、行数或告警数量直接推出根因。

#### B 注释质量

注释须与实现、caller和真值一致；必要时解释为什么、不变量、单位、约束、ownership和历史取舍。纠正过时或误导内容，删去无信息的代码复述，不制造噪音；不能冒称测试覆盖或把推断写成已验证事实。代码表达改善后，仍保留无法由代码直接表达的领域知识。

#### C 高内聚低耦合

职责清楚，状态有明确写入Owner；业务规则、IO、状态推进和呈现各有边界。逐项核隐式全局、反向依赖、过宽上下文、无关参数和跨层状态修改；不能只按单文件判断整个模块的耦合。

拆分须有真实调用、数据流和生命周期证据。按适用范围核热点计算、重复IO、缓存/队列/资源无界增长；性能改善须有实际输入与观察，不为猜测的未来负载增加复杂度。

#### D 可复用

先比较输入、业务语义、失败策略和生命周期，再决定共享。相同片段不等于同一业务合同；检查重复知识、模式布尔值、万能helper和为未来需求建立的抽象。复用应减少共同修改点并保持职责清楚，不能靠扩大上下文或增加隐式依赖消除表面重复。

#### E 测试质量

逐例核真实caller、独立oracle、合法typed fixture、反例、隔离、排重与判别力。不复制实现当oracle，不clone自比，不恒真，不以mock次数冒充业务结果。必要结果可以成组断言，不把无关输入轴或调用层塞进万能用例。类型合同走typecheck；全绿、数量和覆盖率不能单独代表accept。

已证重复、无业务执行或弱断言的用例应精简或补强；删除/合并须保留旧合同→新用例/退出依据的映射，证明必要断言未漏迁，未知候选不自动删除。核心强转、核心mock、放宽timeout、ignore或排除不能掩盖非法输入或执行缺口。

测试判别力存疑或真实缺陷修复需要可证伪反例；有效反控须因指定业务断言失败，保留执行身份及恢复证据，collection/runtime/环境失败不给反控信用。完整要求见[测试质量验收](agent-workflow.md#测试质量验收用户-2026-10-03-固化)，catalog/report/evidence配对按[测试治理](../testing/governance.md)。不为每个已充分支撑的断言重复制造反控。

#### F 可读性

命名达意、函数职责容易说明、控制流平滑，通过代码表达意图。发现必须靠注释补救的命名、结构和控制流问题即登记；“不需要注释才能看懂”不否定B维必要的机制、不变量和历史知识。缩短代码、增加缩写或堆叠表达式不自动提高可读性。

#### G 简洁性与无多余部分

逐文件核死参数、死导出、无用分支、重复防御和可有可无的中间层，回答“删除它会影响什么”。删除前核真实输入、动态使用、公共合同和替代证据，未知项不自动删除。最少文件、类、函数或行数不是独立验收目标。

#### H 可测试性

检查设计是否允许直接验证纯逻辑、隔离副作用、控制时间与随机性，并观察真实结果。可测试性差即使测试全绿仍需登记设计问题。依赖注入按实际需要使用，不能为测试增加万能上下文、无必要的工厂/接口或层层mock；不为方便测试暴露私有状态或扩大公共API。

### 2. 定位问题并选择整改

量化工具只做阅读线索：单函数圈复杂度>10、明显重复块等标记重点读域，记录工具/版本/口径；不为降低数字改代码，不把初筛当验收。

问题同时记录事实分类（已证缺陷/可改善结构/未知）、实际影响、阻断性、处理或保留理由。能够证明维护成本、收益清楚且在授权范围内的重要结构问题，纳入有限批次整改；不能全部转成未来候选。收益不明确的偏好改写可保留并说明权衡；重要未修问题或关键未知保持review/blocked/rework，不用开卡替代闭环。

先确定职责、状态Owner和依赖方向，再决定文件/目录组织。允许拆分、合并、重命名和调整目录，不能拘泥于旧组织形式。同步真实caller、导入/公共出口、测试路径与身份、文档和账本映射；保留Git沿革，不把移动文件当成已完成核验。通常2–4文件或一个可独立审查的模块切片，必要重组按明确模块边界控制。

行为修复先写真实失败反例，再修复并跑相邻回归。纯重构先建立可靠行为基线，再验证行为保持和结构改善，无需伪造产品失败；两类变更分提交。不得修改生成物替代上游修复，不主动恢复退役兼容路径，也不降低lint/typecheck/格式或验收规则。

### 3. 分派、独立审查与责任

- Codex：选择不重叠工作包、核前提/范围/风险并指定Owner；按下述证据验收协议核候选、实际差异、关键证据与风险，独立作接收/返工/集成裁定。默认不重复贡献者的全文审查或重跑已有可靠结果；只有具体风险、矛盾或缺证据才定向进入源码。不能只凭自报passed或包绿裁定。
- 受委派贡献者：全文审查、问题归因、方案、获准范围内编码、测试和可复验交付。本轮存量复审由GLM承担主要执行；该分工不是所有未来任务的固定模型席位要求。
- 用户：决定尚未授权的产品取舍、关键未定前提与不可逆操作；技术核验由Agent承担，不反复请求已给出的授权。

同一实现文件同一时间只有一位Coding Owner；只读试审和产品build分开准入。新方法首批校准后，直接分派有限范围的审查与已获准整改，不把每批纯只读试审或Codex重复全文当作前置门。贡献者自验不能代替Codex独立验收，固定三贤人签字不恢复。隔离、分支及共享树规则按[现行工作流](agent-workflow.md)。

用户2026-10-18补充：可一次委派大型持续目标，贡献者在授权范围内自主拆成2–4文件或清晰模块切片，连续执行，不把每片验收变成用户两边转话的停点。以完整模块/阶段冻结提交与证据、集中据证验收和集成；片级范围/Owner/八维依据仍可追溯。新的产品裁决、实际Owner冲突或证据异常才升级，且只暂停受影响范围；其它独立工作继续，不以大任务名义扩大高风险授权。

### 4. 交付可独立复验的证据

每批提供一个稳定入口，可复用现有任务/评审记录；小改紧凑记录，较大改动形成完整证据包，不为填表另造平行状态源。至少包含：

| 项目 | 最低可复验内容 |
|---|---|
| 候选身份 | 基点与候选完整Git提交/文件指纹；相关caller、依赖、测试及工具版本；未提交候选明确标注，不能冒称已冻结提交 |
| 结论索引 | 按文件的八维结论、具体源码/来源锚点、问题与保留理由；关键claim有适用边界和可推翻条件 |
| 合同映射 | 旧→新文件/出口/测试身份及断言合同去向；删除、合并和N/A可解释，不能漏项后声称等价 |
| 执行事实 | 实际command、cwd、时间、exit、signal/spawn错误、测试file×fullName/状态集合；保留必要的完整原始输出、原生结果及校验值 |
| 诊断与限制 | error/warning/info、运行时诊断、跳过/未跑项和缺口；退出码0带诊断不能写成干净通过 |
| 复验入口 | 快速检查命令、定向验证命令、预期结果、工具版本与限制；源码优先Git提交/blob定位，避免反复复制整份源码 |
| 失效条件 | 哪些实现、caller、依赖、输入域或合同变化会令哪些claim待复核；不能只校验被测文件哈希 |

快速检查默认只读，核版本匹配、附件完整性、原始结果/诊断和映射，不默认修改工作树、联网取证或重跑全仓/覆盖率。可直接组合已有工具；检查器须区分匹配/失败/证据过期/不能自动验证，不能把缺证据当通过。后续接手先快检，再按需定向验证，只重读失效或有疑点的结论及代码范围，复用仍有效的审查成果。

关键结构结论尽量建立可执行约束：例如IO/规则分离提供依赖边界检查及纯规则直接测试，泄漏修复提供真实生命周期反例。哈希证明身份，测试/约束支持指定合同；两者不能自动证明设计优良。语义判断仍由本轮审查完成并留具体依据，不能以恒真脚本、八句自述或“passed”字段替代。

证据产生者和验收规则的变更单独评审；贡献者不能一边改业务一边放宽判据。原始失败按时点保留，后续纠正附新结果；附件移动须同步指针，不改原始字节。避免自嵌哈希、循环认证和给review无限再造review。本页规定交付要求，不宣称已经提供了一个能自动认证全部语义的统一检查器。

### 4.1 贡献者交付与Codex证据验收协议

用户2026-10-18明确：委派的目的是由贡献者承担主要工作、节约Codex token，不能把独立验收变成第二次完整治理。**全文八维审查由Coding Owner承担；独立指裁定与核验责任独立，不要求重复生产全部审查和测试证据。**本协议适用于存量治理和新开发，不削弱八维、零诊断或风险准入。

#### 一份交付、分层展开

每批在原任务提供一个入口，先给可直接裁定的短回执，详细记录和原件按需展开。优先复用原卡/现有工具和同一运行结果；不为每个claim复制源码、日志或新建脚本。不把“尽可能多证据”实现为更多重复表格和附件。

| 交付层 | 贡献者必须提供 | Codex默认消费 |
|---|---|---|
| 裁定页 | 基点/候选SHA、白名单与实际增改删/移动清单、完成/未修/越界项、风险及请求裁定、快检入口、质量门摘要 | 全读短回执，确认本批授权和剩余项；不据摘要直接认证代码 |
| 文件/claim索引 | 每文件A–H具体结论；关键结论的稳定ID、path+symbol+版本锚点、caller/合同、事实/推断/未知分类；行为/结构/注释/测试变化分别定位 | 检查缺维、矛盾、影响域与claim→证据引用，按风险选择需要展开的项；不重读全部文件 |
| 可复验原件 | 完整diff；关键claim对应的测试file×fullName与独立oracle、实际命令/环境/exit/诊断、完整raw/native；必要失败/恢复原件；删除/合并合同和身份映射 | 快检来源/字节/结果集合与真实差异；已有可信同候选结果直接复用，不习惯性再跑 |
| 设计依据 | C/D/F/G/H结论给实际依赖方向/状态Owner、删除影响、抽象取舍与具体例子；有重构时写前后责任边界和行为保持证据 | 阅读取舍及变更切片；无法自动验证的设计结论明确依赖贡献者审查，不伪称机器证明或自动判pending |
| 失效与复验 | 哪个实现/caller/依赖/合同变化影响哪个claim，快检的预期状态和定向命令；业务、工具及流程绑定分开 | 只重验失效claim；流程文字变化不自动重跑未变的产品测试，不因一处漂移重置全批 |

关键claim须给可推翻条件和有效证据，不给每句说明强造反控。行为修复保留红例→修复→恢复；纯重构用行为基线/依赖边界与相邻回归；注释修订用固定源码/真值锚点，标题改名另给身份映射。只读未修改的结论由贡献者负责全文审查与来源说明，不要求Codex再全文证明其读过；指纹只证明身份，不能证明阅读或设计质量。

#### Codex默认验收路径

1. 只读快检候选、白名单、附件完整性、实际原生结果/诊断、合同映射和当前依赖。没有通用检查器时组合现有consumer及明确命令；不能把作者写的verified/pass字段当结果。检查规则或证据产生者有变化时先单独核其差异，规则稳定后复用，不每批重新设计。
2. 阅读短回执、相关八维结论与实际变更切片。普通文案/边界清楚的测试或重构，材料一致且风险已覆盖，可据证裁定；无需通读所有受审实现、所有caller和未变测试。对C/D/F/G/H，核作者具体论据与所改边界，不机械重做其整套推导。
3. 新产品取舍、schema/save/migration/资产或接口、机制真值冲突等高风险，仅加核受影响primary与关键实现/调用边界。普通批次也可按具体疑点作定向抽核；无固定全文复审比例，不每批再跑全套定向/相邻。扩大阅读或执行前记录触发原因、要验证的claim和停止条件。
4. 版本过期、结果不匹配、漏迁合同、论据与diff矛盾或关键项无法复验时，先要求贡献者补该项。发现虚假/系统性不可靠证据才扩大相关范围并撤回相应信用，不默认把作者工作全部自己重做。缺口保持review，已支撑的无关结论保留。
5. 记录accept/rework/review：具体接收的文件/claim、依赖的贡献者证据、Codex实际核过的命令/差异/抽核、未核和未跑项、剩余风险。**不要求“Codex再次全文读完”才可关闭文件**；八维/必要证据和整改仍须完整，作者自验不能自行关闭，Codex须明确作出基于证据的独立裁定。代码验收与全仓集成门仍分开。

贡献者可以在已批准白名单内直接审查并完成必要整改，无需逐文件先交只读报告等第二轮开工；未授权的行为/格式取舍继续停线。接收后滚动下一批，只有方法改变或证据失真才重新校准。验收目标是用更少重复工作获得足够可靠的结论，而非制造更多治理材料。

### 5. 按影响范围验证并集中收口

小批先运行必要的定向/相邻验证、受影响typecheck和静态门；相同候选与相同输入已有可靠结果时复用，不无理由重跑。新变化、失败或未解风险才扩大验证。

全仓check、官方coverage ratchet和protected fast在完整模块或较大稳定任务收尾窗口集中执行，不因每改几个小文件重复运行。测试精简后的官方基准也在该窗口实测；合理覆盖率变化须给解释和必要基准审查，不能堆弱测试或降规则。每项门按当前任务实际需要记录，不把延后写成已通过。

用户2026-10-21补充执行节奏：默认累计多张相关任务卡后再统一运行上述昂贵门，不能把每张卡或每个2–4文件切片都当成全仓测试窗口。卡内仅运行本次改动所需的定向/相邻测试与静态检查；未变候选的可靠结果直接复用。收尾前先冻结本窗口卡清单和代码，再顺序执行统一门；因具体失败必须提前扩验时记录原因与范围。卡内审查结论、统一门和合并分别登记，延后大门期间不提前声称集成收口。

lint、格式、typecheck等硬静态门error/warning/info全部为0；退出码0带诊断不算通过。统一质量门尚未清零时不宣布集成收口，不以存量诊断、ignore/exclude、强转或弱断言豁免。原始历史计数不倒写成0，定向通过不替代runtime/E2E/视觉或部署验收。

运行诊断计数还须证明日志可见。Vitest等工具可能在Agent环境自动使用隐藏通过用例日志的reporter；此时exit0且raw无诊断只证明“无可见诊断”，不能写零诊断。选用显式default等保留全部日志的reporter，或记录经已安装工具源码验证的进程级探测环境调整；同时保留stdout/stderr完整原件。不得修改console、测试选择、超时或规则以制造零诊断。

## 失败处理

一手证据冲突、关键前提未知、重要问题未闭合或候选发生相关漂移时，停止受影响步骤并明确解除条件。涉及schema/save/migration/资产管线、公共接口、机制真值或可感知行为时核实际授权和风险；已有授权内继续，新的产品取舍或不可逆操作才交用户裁决。按原任务升级风险，不把本规范当无限产品build授权。

快检失败或证据过期须定位具体claim和文件，不一概重置全仓结论，也不机械重做全部审查。发现作者报告与代码/原件不符，撤回受影响信用并扩大必要复核；不得修改验收规则让错误报告过门。共享树有其他Owner改动时保护原件，不覆盖、reset或擅自stash。

## 完成定义

- 审查完整：受审文件八维均有具体结论，读域、caller与证据边界明确；历史状态不自动转换。
- 整改完成：必改项已解决，保留项有充分理由且不掩盖关键未知，结构改善有具体收益与行为证据。
- 可集成：Codex独立审查与任务要求的质量门已通过，映射/文档/记录同步，必要产品取舍已获授权。三者分别记录，不能互相替代。
- 本规范接入完成只证明长期入口、流程和模板生效；不证明任何存量文件已完成八维复审，也不改变代码账本的关闭数。规范变更按[项目文档模型](guides/documentation-model.md)同提交写回并验证。
