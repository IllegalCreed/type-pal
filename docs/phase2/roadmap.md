# 第二阶段路线图 — 重制引擎 + 内容编辑器

> 状态：活文档（2026-06-17 起草，2026-07-13 补全执行路线）。本文是第二阶段的**总纲 / 北极星**，只定方向、依赖顺序与完成口径；每项实现细节另见能力地图、任务卡和各自 spec。
> 文档边界：`docs/` 顶层与 `docs/plans/` 服务**第一阶段（忠实还原）**，本目录（`docs/phase2/`）服务**第二阶段**。两者不混。

## 0. 三阶段愿景

| 阶段 | 目标 | 状态 |
|---|---|---|
| 一 | 100% 忠实还原原版仙剑（字节级对齐 pal.exe） | 接近尾声 |
| 二 | 在还原成果上**修改 / 创作**自有内容，逐步替换原版资源，清版权 | ← 本文 |
| 三 | 基于第二阶段成果制作 MMO | 远期 |

## 1. 第二阶段是什么

把项目从「只能播放原版内容的忠实复刻」，升级为「能用编辑器**自己生产内容**的现代化引擎」。两件大事：

1. **新引擎**：现代化、场景解耦的运行时，替换掉为忠实还原而生的全局耦合数据模型。
2. **内容编辑器**：可视化编辑地图、场景事件、数据表，产出独立于原版的内容工程。

完成后，创作新内容不再依赖从原版 MKF 提取；原版资源逐步被自有资源替换。

## 2. 硬约束（已与作者对齐）

- 内容源**独立、版本化**；初始化 = 从 `data/extracted/` 复制一份，此后独立演进。
- 事件编辑**必须可视化**（不要求作者读字节码）。
- 现有 `@type-pal/game` 引擎**冻结不动**，新引擎另起 package。
- 新引擎**现代化**：场景自包含（map + sprites + events 随场景按需加载），跨场景影响走全局层；消除 `all.json` 全局脚本、per-role HP 这类全局耦合。
- 为第三阶段 MMO **预留状态分层**（玩家私有 vs 世界共享），不挖死胡同。

## 3. 关键架构判断

1. **旧 game / 原版 = 内容参考，不是实现真值锚。** 第二阶段是全新创作：新引擎**不要求行为与旧 game / 原版逐状态一致**，没有「双引擎对照」（那是第一阶段打法）。旧 game 与原版只用来回答「这场戏 / 这个系统原本是什么样」，作内容与玩法参照；实现怎么做、数据怎么放，由新架构自己定。
2. **架构全新重写，移植已验证的逻辑知识。** 战斗公式、164 个 opcode 语义、present 渲染数学是几十个 commit 啃出来的**知识** → 可移植 / 重新实现，但**不照搬旧的模块结构**（那会把旧架构的耦合一起带进来）。新引擎从架构出发重新组织。
3. **真正的地基是内容 schema。** 引擎与编辑器都长在其上。「场景层 vs 全局层」的边界是第二阶段最核心的设计。
4. **引擎先吃通 schema，再做编辑器。** 否则 schema 未经运行验证，编辑器返工。
5. **schema 给 MMO 留口。** 状态分层（玩家私有 / 世界共享）在单机阶段就埋好。
6. **杜绝「下标 / 数组位置当身份」。** 对象、引用、状态键一律用稳定 id / 语义名 —— 加删内容不牵动他者、跨场景引用可读可编辑。解耦与编辑器友好的硬性原则。

## 4. 顶层分解

| 子项目 | 内容 | 依赖 |
|---|---|---|
| **P0 · 内容 Schema + 迁移器** | 定义场景自包含的内容格式 + 全局层边界；写 `extracted → 内容工程` 的一次性迁移 | — |
| **P1 · 新引擎 package** | 架构全新重写，移植已验证逻辑（战斗 / opcode / 渲染），按 P0 schema 组织、场景懒加载；核心系统（对话 / 战斗 / 存档 / 事件）逐步重做；验收 = 正确跑迁移内容 + 架构现代化 / 解耦 / 可扩展 | P0 |
| **P2 · 编辑器 package** | 读写内容工程：地图笔刷 + 可视化事件编辑 + 数据表编辑；嵌 P1 做实时预览 | P1 |
| P3 · 素材创作管线 | 导入 / 创作自有美术（瓦片 / 精灵）、音乐、字体，替换原版资源（市面工具 vs 自研待定） | P2 |

依赖链：**P0 → P1 → P2 → P3 → P4**。每个子项目各走一遍 spec → plan → 实现，各自出独立文档。

## 5. 切入策略：骨架先行 + 垂直切片

不在白板上把 schema 一次设计完美（瀑布陷阱）。P0 先定 schema **骨架**（重点是场景层 / 全局层边界），立刻用 P1 一个**垂直切片**验证：让新引擎跑通一个最简单的场景，边跑边补。

**首个垂直切片目标（暂定，作者可调）**：一个室内小场景（客栈 / 民居类）—— 加载地图 + 几个 NPC + 一段对话，在新引擎跑通；编辑器能改对话、加一个 NPC。作为第一个看得见摸得着的 milestone。

## 8. 北极星与原版定位（2026-07-04 重组，废原 §8「100% 复刻 = 验收」）

> **本节取代旧 §8「硬验收：完整复刻原版」。** 旧版把「原版全流程通关 = 验收」钉成 done 标准，与铁律 #6（现代化优先，不复刻怪癖）直接冲突，导致每步推进都在「要不要为复刻忍脏」上反复拉扯。

### 北极星（用户 2026-07-04 原话定调）

> **一个现代化、先进、合理的引擎 + 一个编辑器，用户能用它创建新内容、新游戏包，甚至制作一款全新的游戏（素材剧情全替换）。**

判据层级（从高到低）：
1. **架构层** —— 一个领域改内部实现，不牵动别的领域（`@type-pal/content` 契约切干净）。这是「现代化」的硬定义。
2. **能力层** —— [能力地图](capability-map.md) 上的格，引擎能跑 AND 编辑器能编。
3. **内容层** —— 能用这套平台跑原版内容（回归沙盒）+ 创作新内容。

### 原版仙剑的三条用法（不再是验收标准）

| 用法 | 判据 | 动作 |
|---|---|---|
| **A · 试炼场** | 一格 done = 能在原版找到**至少一个**真实例子跑通，**不要求**全覆盖 | 每格点名一段原版当考题；考题过 = done |
| **B · 第一份内容包** | 迁移器产物能在新引擎实际玩起来；覆盖度**不作里程碑门** | 维护回归沙盒（[capability-map §6](capability-map.md)）；能玩打✅，跑不了标缺啥 |
| **C · 迁移器练手对象** | 翻译成现代 schema，覆盖率可量，未覆盖有账 | 迁移器 pending 项是「翻译待办」，不是「验收欠款」 |

**红线（铁律 #6 不让步）**：原版隐式怪癖机制（冻帧副作用、palette 轮转、下标当身份…）**不进新引擎**。非要靠脏耦合才能跑的原版编排 → 标回归沙盒「需重写脚本」，不把脏东西搬进引擎。

### M1–M4 不作废

它们是**已 done 的能力格的历史名字**（M1=数据格 / M2=场景格 / M3=叙事格 / M4=战斗格进行中）。以后不再用里程碑编号，直接用格 id。详见 [capability-map §7](capability-map.md)。

## 9. 能力地图 + 下一步选择器（2026-07-04 新增）

第二阶段「做成什么样 / 做到哪了 / 下一步做啥」的真值，全部收敛到 **[能力地图 capability-map.md](capability-map.md)** —— 它取代旧 §8 复刻矩阵当进度真值表。

**核心机制（一句话）**：7 领域、40 格；一格 done = 引擎能跑 AND 编辑器能编；下一步不靠直觉，跑[选择器](capability-map.md#5-下一步选择器每次开工先跑这个)读图。

每次开工标准动作：
```
1. 读 capability-map §5 选择器 → 决定下一步格
2. 该格的原版考题 → 进 docs/phase2/<领域>/ 找/写 spec
3. 实施（引擎侧 + 编辑器侧两边都 done 才算）
4. 更新地图（该格标✅）+ 回归沙盒（考题跑通打勾）
5. 下一轮回 1
```

能力地图是**活文档**，撞到原版新东西就加格（[发现协议](capability-map.md#8-能力格发现协议地图怎么长大)）。原版一个脏机制在新地图里常裂成多格（冻帧 → E6/N7/E7 三格）。

## 10. 从当前工程到完整产品的执行路线（2026-07-13）

### 10.1 四份真值各管什么

聊天记录不承担路线图职责。以后用户追加长期目标，先写回本节或能力地图，再开任务卡。

### 10.2 最终完成不是一个 `done`

第二阶段必须同时达到五个终点，缺一项都不能称为完整产品：

1. **创作平台完成**：新引擎能运行、编辑器能创作完整 RPG 内容，稳定 schema 上的常用工作流无需手改 JSON。
2. **首个内容包完整可玩**：迁移后的 `projects/pal` 能从开场一直走到结局；不是只验证若干能力考题。
3. **工程资源自包含**：工程运行所需内容与素材全部在工程目录内，运行时不再偷偷读取仓库级 `/extracted`、`/baked` 或其他外部素材目录。
4. **替代资源完成**：原版受保护素材按清单逐批替换，自有资源有来源、生成记录和视觉验收。
5. **可独立发行**：能产出带运行壳的可玩包；A5 的“工程 zip 备份”不等于独立游戏发行包。

### 10.3 执行波次

| 波次 | 主任务 | 关键产物 | 退出条件 |
|---|---|---|---|
| R0 | 基线收口 | 路线图、能力地图、任务看板口径统一 | 本节落库；当前工作只从看板进入 |
| R1 | **N6 共享脚本/子程序** | 作者脚本库、引用编辑、保存/重迁移闭环 | 同一脚本被多处调用，改一处全部生效；MG2 重迁不丢；三方验收 |
| R2 | 迁移残余收口 | `unmigrated`、错误映射、悬空边与人工 overlay 分类账 | 能上游修的全部先修迁移器并重生成；剩余项逐条有“源数据无效/明确不支持”证据；双跑零计划与 M3 体积门禁继续成立 |

| R8 | 自有资源替换 | 完整资源盘点、批次生成/导入、替换登记、视觉回归 | 发布目标范围内不再依赖原版受保护表达；每批有可追踪验收 |
| R9 | **A8 独立可玩发行包** | 运行壳 + 工程内容/资产 + 构建/校验命令 | 在不依赖本仓库源码、`data/`、`projects/` 外部目录的干净环境中可启动并完成代表性 E2E |

当前从 **R1** 开始，任务卡为 [N6 共享脚本/子程序创作闭环](../ops/tasks/N6-shared-script-authoring.md)。R1 完成后按 R2 推进；任何 E2E 暴露的迁移器根因仍遵守“先修上游、再重生成”的最高优先级规则。

### 10.4 Q1 全流程 E2E 硬契约

[碎片地图与检查点台账](../../projects/pal/e2e-checkpoints/README.md)继续作为每段边界与验证点的真值。实现不得把它降格成几条冒烟测试：

- 整个游戏切成数百个小段；每段有可执行流程脚本、明确起点/终点和断言。
- 001 从全新游戏开始。除 001 外，每段起始存档必须由上一段**真实执行后的结束状态**生成；禁止手工伪造一份看似能跑的剧情状态替代链路。
- 第 N 段的结束存档就是第 N+1 段的起始存档；文件记录来源段、生成提交和必要的内容版本，能检查链路漂移。
- Q1 只验证剧情、场景、演出、菜单接续和存档连续性。遇到任何战斗，runner 直接取得胜利结果，但仍走正式胜利结算、奖励和胜利剧情分支，保证下一段存档合法。
- 战斗系统另建 **Q2 隔离测试**：固定队伍/敌队/随机种子，覆盖指令、公式、AI、状态、动画与结算；Q2 禁止使用 Q1 的速胜旁路。
- 前 10 段先证明 runner、检查点和调试成本可控，再批量扩展。R5 是长期流水线，可与 R6-R8 穿插，但存档链必须按顺序增长，不能跳段造档。

### 10.5 工程自包含与发行边界

- **A5 工程 zip**：用于备份/交换可编辑工程，内容是工程目录本身。
- **A7 资源闭包**：保证这个工程目录确实包含运行所需的全部项目资源，所有加载都经 manifest 与 `FileSource`。
- **A8 独立发行包**：在 A7 之上再带可执行的 Web 运行壳和版本化构建产物，面向玩家，不要求玩家安装仓库依赖或打开编辑器。

A7 必须先于大规模 E2E：否则流程跑到后半段才发现某类头像、音乐、RNG、字体或音效仍从仓库外取，会让检查点和发行验证一起返工。

### 10.6 替代资源原则

- AI 生图和批量替代资源的 Generation Owner 固定为 Codex；Opus/GLM 负责方向压力测试、覆盖清单和风险审查。
- 先建资源清单与引用闭包，再按“UI 通用件 -> 场景瓦片 -> 角色/敌人 -> 立绘/头像 -> 过场 -> 音频”分批替换；不得靠搜索到一张就随手覆盖。
- 每项记录原用途、替代资产、尺寸/格式/透明度/动画约束、生成或授权来源、引用位置和验收截图。
- 替代目标是功能与叙事角色等价，不复制原版受保护的具体构图、造型和像素表达。
