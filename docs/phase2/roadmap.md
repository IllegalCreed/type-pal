## 1. 第二阶段是什么

把项目从「只能播放原版内容的忠实复刻」，升级为「能用编辑器**自己生产内容**的现代化引擎」。两件大事：

1. **新引擎**：现代化、场景解耦的运行时，替换掉为忠实还原而生的全局耦合数据模型。
2. **内容编辑器**：可视化编辑地图、场景事件、数据表，产出独立于原版的内容工程。

完成后，创作新内容不再依赖从原版 MKF 提取，并具备导入、替换和自包含分发作者资源的完整能力；
原版受保护资源的实际批量替换与版权发布验收归第三阶段。

## 2. 硬约束（已与作者对齐）

- 内容源**独立、版本化**；初始化 = 从 `data/extracted/` 复制一份，此后独立演进。
- 事件编辑**必须可视化**（不要求作者读字节码）。
- 现有 `@type-pal/game` 引擎**冻结不动**，新引擎另起 package。
- 新引擎**现代化**：场景自包含（map + sprites + events 随场景按需加载），跨场景影响走全局层；消除 `all.json` 全局脚本、per-role HP 这类全局耦合。
- 状态分层按**当前产品需要**设计（玩家私有 / 世界共享边界清晰）；不为 MMO 预留额外口子——
  第三阶段 backlog 已明确裁决（见 [`docs/phase3/backlog.md`](../phase3/backlog.md)）。
- **开发期 current-only**：正式上线前只支持当前 canonical 内容/存档格式；一次重迁完成后，同任务删除旧
  upgrader、旧类型、fixture、版本分支、产品升级入口与兼容 fallback，历史由 Git 保存。

## 3. 关键架构判断

1. **旧 game / 原版 = 内容参考，不是实现真值锚。** 第二阶段是全新创作：新引擎**不要求行为与旧 game / 原版逐状态一致**，没有「双引擎对照」（那是第一阶段打法）。旧 game 与原版只用来回答「这场戏 / 这个系统原本是什么样」，作内容与玩法参照；实现怎么做、数据怎么放，由新架构自己定。
2. **架构全新重写，移植已验证的逻辑知识。** 战斗公式、164 个 opcode 语义、present 渲染数学是几十个 commit 啃出来的**知识** → 可移植 / 重新实现，但**不照搬旧的模块结构**（那会把旧架构的耦合一起带进来）。新引擎从架构出发重新组织。
3. **真正的地基是内容 schema。** 引擎与编辑器都长在其上。「场景层 vs 全局层」的边界是第二阶段最核心的设计。
4. **引擎先吃通 schema，再做编辑器。** 否则 schema 未经运行验证，编辑器返工。
5. **状态分层按当前产品需要设计。** 玩家私有 / 世界共享边界在单机阶段就埋好——这是当前产品自身的
   架构需要；不为 MMO 预留额外口子（后续裁决见 phase3 backlog）。
6. **杜绝「下标 / 数组位置当身份」。** 对象、引用、状态键一律用稳定 id / 语义名 —— 加删内容不牵动他者、跨场景引用可读可编辑。解耦与编辑器友好的硬性原则。

## 5. 切入策略：骨架先行 + 垂直切片

不在白板上把 schema 一次设计完美（瀑布陷阱）。P0 先定 schema **骨架**（重点是场景层 / 全局层边界），立刻用 P1 一个**垂直切片**验证：让新引擎跑通一个最简单的场景，边跑边补。

**首个垂直切片目标（暂定，作者可调）**：一个室内小场景（客栈 / 民居类）—— 加载地图 + 几个 NPC + 一段对话，在新引擎跑通；编辑器能改对话、加一个 NPC。作为第一个看得见摸得着的 milestone。

## 8. 北极星与原版定位（2026-07-04 重组，废原 §8「100% 复刻 = 验收」）

> **本节取代旧 §8「硬验收：完整复刻原版」。** 旧版把「原版全流程通关 = 验收」钉成 done 标准，与铁律 #6（现代化优先，不复刻怪癖）直接冲突，导致每步推进都在「要不要为复刻忍脏」上反复拉扯。

### 北极星（用户 2026-07-04 原话定调）

> **一个现代化、先进、合理的引擎 + 一个编辑器，用户能用它创建新内容、新游戏包，甚至制作一款全新的游戏（素材剧情全替换）。**

判据层级（从高到低）：
1. **架构层** —— 一个领域改内部实现，不牵动别的领域（`@type-pal/content` 契约切干净）。这是「现代化」的硬定义。
2. **能力层** —— [能力地图](capability-map.md) 上的格，引擎能跑 AND 编辑器能编。
3. **内容层** —— 能用这套平台跑原版内容（回归沙盒）+ 创作新内容。

### 原版仙剑的三条用法（不再是验收标准）

| 用法 | 判据 | 动作 |
|---|---|---|
| **A · 试炼场** | 一格 done = 能在原版找到**至少一个**真实例子跑通，**不要求**全覆盖 | 每格点名一段原版当考题；考题过 = done |
| **B · 第一份内容包** | 迁移器产物能在新引擎实际玩起来；覆盖度**不作里程碑门** | 维护回归沙盒（[capability-map §6](capability-map.md)）；能玩打✅，跑不了标缺啥 |
| **C · 迁移器练手对象** | 翻译成现代 schema，覆盖率可量，未覆盖有账 | 迁移器 pending 项是「翻译待办」，不是「验收欠款」 |

**红线（铁律 #6 不让步）**：原版隐式怪癖机制（冻帧副作用、palette 轮转、下标当身份…）**不进新引擎**。非要靠脏耦合才能跑的原版编排 → 标回归沙盒「需重写脚本」，不把脏东西搬进引擎。

### M1–M4 不作废

它们是**已 done 的能力格的历史名字**（M1=数据格 / M2=场景格 / M3=叙事格 / M4=战斗格进行中）。以后不再用里程碑编号，直接用格 id。详见 [capability-map §7](capability-map.md)。

## 9. 能力地图 + 下一步选择器（2026-07-04 新增）

第二阶段「做成什么样 / 做到哪了 / 下一步做啥」的真值，全部收敛到 **[能力地图 capability-map.md](capability-map.md)** —— 它取代旧 §8 复刻矩阵当进度真值表。

**核心机制（一句话）**：8 领域、63 格；一格 done = 引擎能跑 AND 编辑器能编；下一步不靠直觉，跑[选择器](capability-map.md#5-下一步选择器每次开工先跑这个)读图。

每次开工标准动作：
```
1. 读 capability-map §5 选择器 → 决定下一步格
2. 该格的原版考题 → 进 docs/phase2/<领域>/ 找/写 spec
3. 实施（引擎侧 + 编辑器侧两边都 done 才算）
4. 更新地图（该格标✅）+ 回归沙盒（考题跑通打勾）
5. 下一轮回 1
```

能力地图是**活文档**，撞到原版新东西就加格（[发现协议](capability-map.md#8-能力格发现协议地图怎么长大)）。原版一个脏机制在新地图里常裂成多格（冻帧 → E6/N7/E7 三格）。

### 10.2 最终完成不是一个 `done`

第二阶段必须同时达到四个终点，缺一项都不能称为本阶段完成：

1. **创作平台完成**：新引擎能运行、编辑器能创作完整 RPG 内容，稳定 schema 上的常用工作流无需手改 JSON。
2. **首个内容包完整可玩**：迁移后的 `projects/pal` 能从开场一直走到结局；不是只验证若干能力考题。
3. **工程资源自包含与预制发布源**：工程拥有的运行内容与素材全部在工程目录内，运行时不再偷偷读取仓库级 `/extracted`、`/baked` 或其他外部素材目录；默认 UI、字形、光标和标题由引擎壳随 bundle 提供，不复制进工程。A1 服务器版本化预制工程资源库在第二阶段最终发布前收口。
4. **可独立打包运行与发布协作**：能产出带运行壳的可玩包；A5 的“工程 zip 备份”不等于独立游戏包。
   Q1/Q2 完成后具备 `capture` profile、Content Studio 窄录制适配与分镜映射。第二阶段只验证技术闭包，
   不以替换全部版权素材或公开发行作为退出条件。

#### W8 地图内容选择与实例属性编辑（2026-07-17 新登记）

- “瓦片素材选择”“待盖图章模板”“地图中已放置内容的选区”“当前活动图层”是四种独立状态，不能再共用一个
  `selectedTile` 或 `selection` 概念。取样只形成下一笔画刷，不能冒充对已有内容的编辑。
- 专用选择工具支持单格、拖拽框选、增选/减选、清空；右侧 Inspector 把视觉实例
  (`layerId + row + col` 的 tile 与实例遮挡高度)和格点属性(`row + col` 的独立碰撞)分区显示。多选不同值显示“混合”，
  修改某一字段不得改写其他字段。
- 默认只命中当前活动图层；隐藏层不命中也不可写，锁定层可见但不命中也不可写。其他层变暗只改变显示，不能偷偷改变
  编辑目标；重叠位置通过显式候选列表或 `Alt/Option + 点击`切换，图层改名/重排后仍以稳定 `layerId` 保持选择。
- 移动、复制、剪切、粘贴、删除和批量属性修改都必须是一次可逆命令。普通选区是否包含独立碰撞必须显式显示，不能因
  碰撞叠加层是否可见而暗中改变操作范围。
- 选区是编辑器工作区临时态，不写入游戏内容；属性修改才进入 `EditSession` 并保存。完整设计、测试矩阵和三方门禁见
  [W8 任务卡](../ops/archive/tasks/done/W8-map-content-selection-inspector.md)。

#### W7G 组合地物 / 图章的已拍板需求

完整 schema 设计、S1-S16 未决题、交互/权限矩阵、测试清单和三方门禁见
[W7G 任务卡](../ops/archive/tasks/done/W7G-composite-tile-stamps.md)。该卡已于 2026-07-18 完成三方验收与用户收口；
下列内容是已落地设计约束，不是当前 draft。

- 树、桌椅、屋顶、岩壁等由多个 tile 组成的地物，在编辑器里作为一个可预览、可命名、可分类的图章选择；
  用户画一棵树只需一次落笔，画 100 棵不再重复找碎片。
- 图章模板保存每个组成格的相对位置、视觉图层、tile、**实例高度**与碰撞值；这些属性在制作模板时设置一次，
  每次盖章自动带入，绝不能要求放置后逐 tile 补高度。
- 支持从地图框选“保存为图章”和由 tileset 预置图章；落笔前显示完整幽灵预览，越界/冲突有明确反馈。
- 一次盖章是一个原子命令，可整体撤销/重做；底层仍写入同一 ProjectMap 版本族的普通层、实例高度和独立碰撞，
  运行时不认识图章，也不形成 StampMap/Tilemap 之类第二格式。
- 用户必须能在盖章后、切换工具后以及保存重开后，通过点击任一组成格重新选中整个已放置图章。仅把一次盖章摊平成
  普通格无法可靠区分两个相邻同款图章，因此 W7G 正式设计必须加入**稳定、非链接的作者态放置组身份**；其 schema
  形状、覆盖/重叠/残缺成员/图层删除规则必须在 W7G 自己的三方设计卡中定案，不能偷塞进 W8。
- “整章选择”和“进入组内改单格”必须是明确的两级操作，并提供“解组但保留格子”。图章模板修改或删除不联动既有放置；
  这不是 linked prefab。跨图层图章的移动、复制、删除和撤销必须全有或全无，任一目标层隐藏/锁定/缺失时不得静默只改一部分。
