# 02 · 架构设计

## 两阶段:离线转换 + 运行时

整个项目分成**两个独立的部分**,中间隔一道墙。

```
═══ 阶段一 · 离线转换(独立工具,只跑一次)═══

  MKF 文件 ──▶ [pal-extract 工具] ──▶ 现代项目资源
                                     ├ images/*.png      精灵图集
                                     ├ maps/*.json       瓦片地图
                                     ├ data/*.json       物品/法术/怪物/场景表
                                     ├ audio/*.ogg
                                     ├ video/*.mp4
                                     └ events/*.json     事件 / 编排
   ▲ MKF 在整个项目里只在这里被碰这一次。

══════════════════ 墙 ══════════════════
   网页游戏从此只认上面这些文件,代码里没有一行认识 MKF。

═══ 阶段二 · 网页游戏(运行时)═══

  加载 png / json / ogg / mp4 ──▶ 跑游戏
```

- **MKF 解析只活在 `pal-extract` 工具里**,它和网页游戏是两个独立 package。网页游戏代码里没有一行认识 MKF,完全脱离。
- `pal-extract` 是一个 Node 命令行工具,运行一次,产出 `data/extracted/`(现代资源)。

## 资源 vs 事件:两类东西

转换时要分清两类东西,它们性质不同。

**1. 资源(被动数据)** —— 加载后被使用,不含逻辑:

| 原版 | 转成 |
|---|---|
| RLE 精灵 | 索引位图图集(像素 = 调色板下标)+ JSON(帧偏移 / 锚点) |
| 地图瓦片 | JSON tilemap + 瓦片集 PNG |
| 对话 / 文字 | JSON / 纯文本 |
| 数据表(物品 / 法术 / 怪物 / 场景) | JSON |
| 音乐 / 音效 / 语音 | 音乐 `.mid` 原样保留(运行时 SpessaSynth 合成);CD 音轨 / 音效 / 语音转 ogg |
| AVI 过场 | mp4 / webm |
| 调色板 | 单独存(不烤进精灵);水 / 火的**调色板循环动画**一并留成数据。运行时软件查表上色,见 D12 |

**2. 事件 / 编排(行为)** —— 是逻辑,不是被动数据:

原版字节码脚本负责的"剧情 / 事件层",转成**可读的 JSON 事件文件** —— 一条条 event-command(`showDialog` / `walkTo` / `playAnim` / `startBattle` / `giveItem` / `goto` …)。事件模型本身富、结构化优先(`sequence` / `if` / `choice` / `loop` + 动作 + 低层 `label` / `goto`)。但 `pal-extract` 对原版脚本走**忠实转写**(反汇编级:字节码 1:1 转成带标签的命令清单,落在 `label` / `goto` 子集),**不做结构化反编译**(见 D16 / D17)。按场景分文件(D18)。完整 schema 见 `05-events-schema.md`。

关键区别:图片是被"画出来",事件 JSON 是被"执行"。运行时有一个**事件系统**读这些 JSON 并执行它们 —— 这不是仿真器,而是每个现代引擎都有的东西(类比 RPG Maker 的事件指令、Unity Timeline)。`events/*.json` 是"活的"资源文件:在硬盘上、脱离 MKF、人可读,但被执行。

**为什么这样不破坏"忠实"**:字节码 → JSON 的反汇编是无损、可逆的 —— 忠实转写让 `pal-extract` 能 round-trip(JSON 再编译回字节码逐字节比对)验证。"忠实"活在**执行语义**里 —— 只要事件系统每条命令的语义和原版 opcode 一致,存成二进制还是 JSON 都不影响结果。

**扩展靠模型,不靠反汇编**:新剧情 / 任务由人用结构化子集(`if` / `choice` / `sequence`)手写,不经过反汇编器。原版脚本的可编辑性(把 `label` / `goto` 提升成结构化)是第二阶段的可选 pass,以忠实转写产出为测试基准。

## 运行时分层架构

网页游戏(阶段二)内部分四层:

```
┌──────────────────────────────────────────────────┐
│ 外壳层 Shell      主循环 / 键盘输入 / 存档(IndexedDB)│
│                   音频播放 / 资源加载 / 视频过场      │
├──────────────────────────────────────────────────┤
│ 表现层 Present.   渲染(320×200 缓冲 → Canvas 缩放)  │
│                   精灵·地图·文字·转场 / 消息框·菜单·战斗UI│
├──────────────── 命令总线 Command Bus ───────────────┤
│ 核心层 Core       游戏状态 GameState                 │
│ (纯逻辑·可测试)   事件系统 · 场景 · 战斗 · 规则       │
├──────────────────────────────────────────────────┤
│ 资源加载层 Assets  fetch png/json/ogg/mp4(不含 MKF) │
└──────────────────────────────────────────────────┘
```

核心原则:

1. **核心层是纯逻辑**,不碰渲染、不碰 MKF。通过「命令总线」与上层通讯 —— 事件系统不直接画对话框,而是发出 `显示对话` / `播放音效` / `进入战斗` 命令,表现层和外壳层消费。这样核心系统可脱离浏览器单元测试。
2. **所有"内容"都从资源文件来**,核心代码不硬编码任何剧情、地图、数值。
3. **字节码相关的东西被隔离**在事件系统这一个模块里。第二阶段若要加现代脚本 API,是在它旁边并列加,不动它。

## 核心层:1 个状态 + 4 个系统 + 1 条总线

```
                ┌────────────── GameState ──────────────┐
                │  队伍/角色 · 背包/金钱 · 事件对象状态    │
                │  当前场景与坐标 · 游戏进度   (可序列化)  │
                └────────────────────────────────────────┘
                      ▲  所有系统读写这里(唯一真相源)
      ┌───────────────┼────────────────┬────────────────┐
 ┌────┴────┐   ┌──────┴──────┐   ┌─────┴─────┐   ┌──────┴──────┐
 │ 场景系统 │   │  事件系统    │   │  战斗系统  │   │ 规则系统     │
 │ 行走碰撞 │   │ (总导演)     │   │ 回合/公式  │   │ 角色/物品/   │
 │ NPC行为  │   │ 对话/编排    │   │  AI/奖励   │   │ 法术·升级·商店│
 │ 触发检测 │   └─────────────┘   └───────────┘   └─────────────┘
 └─────────┘
```

- **GameState** —— 唯一真相源,可序列化。存档 = 把它 JSON 化;读档 = 还原它,不需要单独的存档系统。注:原版**没有通用标志位数组** —— 剧情进度靠事件对象状态(隐藏 / 正常 / 阻挡)+ 可变的脚本入口指针编码,GameState 直接存这些(见 `05-events-schema.md`)。
- **事件系统** —— "总导演"。绝大多数玩法流程由它串:玩家在 NPC 前按确认 → 场景系统检测到交互触发 → 交给事件系统 → 执行该 NPC 的 `events.json`(对话 → 选择 → 满足条件就调战斗系统 / 改 GameState 给物品)→ 回到探索。NPC 的"自动行为"(闲逛、待机动画)也是事件的一种,由场景系统按帧驱动。
- **场景系统** —— 当前地图、队伍行走、NPC 行为、瓦片碰撞、相机滚动、触发检测。
- **战斗系统** —— 回合制战斗。回合顺序、伤害公式、五行相克、敌方 AI、经验升级、奖励结算。公式最密集的硬骨头,严格照 sdlpal 的 `fight.c` / `battle.c`。
- **规则系统** —— 角色属性、升级、物品定义与效果、法术、装备、商店。

**顶层模式状态机**:`探索 ⇄ 事件/过场 ⇄ 战斗 ⇄ 菜单`。主循环每帧把输入交给"当前模式",各模式互不干扰。

## 表现层 / 外壳层设计

**主循环**(外壳层)—— `requestAnimationFrame` 驱动,固定步长:探索 / 菜单 / 事件 **10fps**、战斗 **25fps**(照原版 `FPS` / `BATTLE_FPS`)。逻辑 = 渲染同帧、不插值 —— 那个 10fps 的节奏就是原版原味。一个 tick = 收输入快照 → 当前模式 `tick()` → 系统跑逻辑发命令 → 表现层消费命令并渲染一帧。全局 `frameNum` 计数器(NPC 动画相位靠它)。切后台回来不补帧。

**输入**(外壳层)—— 监听 `keydown` / `keyup`,把 `KeyboardEvent.code` 映射成**抽象按键**;核心层只见抽象按键,可喂合成输入单测。每 tick 给当前模式一份快照:`held`(按住,走路用)+ `pressed`(本 tick 新按下,菜单用,靠浏览器自动重复天然连续滚)。方向键最新按下优先。键位表可编辑、含 WASD 别名。输入流可录制成序列、确定性回放 —— 自主通关回放测试的基础(见 `06-testing.md`)。

**转场**(表现层)—— 转场(淡入淡出、调色板渐变等,见 D12 软件调色板)是盖在当前模式上的覆盖效果,不是顶层模式。触发它的系统发一条命令后**挂起、跨帧等回执**,转场放完才继续。

**可等待命令** —— 转场、显示对话(等玩家确认)、播放动画(等放完)、播视频 都是「核心发出命令后要等它完成」的命令。命令总线因此不是纯单向 fire-and-forget:存在一类**可等待命令**。事件系统是**协程式步进器** —— 走到这种命令就停在那一步、每 tick 查回执,完成才进下一步。

## 扩展性:怎么兑现"以后好改"

| 想加的东西 | 怎么加 | 动不动引擎 |
|---|---|---|
| 新场景 | 加一个 `map.json` + 一个 `events.json` | 不动 |
| 新物品 / 法术 / 怪物 | 往 `data/*.json` 加一条 | 不动 |
| 新剧情 / 任务 | 写 `events.json` 里的 event-command | 不动 |
| 新玩法机制(如小游戏) | 加一个新系统模块,挂到模式机上 | 只加不改 |

## 技术栈(已确认 —— 见 04-decisions.md D19)

- **语言**:TypeScript。
- **构建**:Vite(网页游戏)。
- **包管理 / 结构**:pnpm workspace monorepo,**3 个 package**:
  - `pal-extract` —— Node 命令行转换工具。
  - `game` —— 网页游戏运行时。
  - `shared` —— 两边共用的 JSON 类型(events.json schema、数据表、资源清单)。
- **渲染**:Canvas 2D + 软件索引帧缓冲(见 D12)。
- **测试**:Vitest(重点测核心层的纯逻辑:战斗公式、事件系统)。
- **格式化 / lint**:Biome。**不做 CI**,用本地 `pnpm check`(类型检查 + 测试)。
- 网页游戏画面是一整块 canvas,**不需要 React/Vue**;只有外壳 UI 用少量 DOM。
