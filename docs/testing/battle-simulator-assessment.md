# 共享战斗模拟器：编辑器全域复用评估

2026-09-19，Codex。关联：[原技能试放卡，现rework](../ops/tasks/EDITOR-SKILL-TRIAL-1-isolated-battle.md)。
性质：**只读评估和方案建议，不是已实现功能或build授权**。产品核对点`1c8cad29`，生产相对`e58834f6`无改动。
按用户要求覆盖完整编辑器目录，不只看技能页；用户提出的我方/敌方配置、预存我方方案、道具使用/投掷和取消开局选择均纳入。

## 结论

应把它设计为**编辑器统一的战斗测试工作台**，以现有第二阶段战斗引擎实际运行，
而不是“技能专用小弹窗”，也不是另写一套简化战斗计算器。
所有战斗相关编辑页都可复用同一配置/启动/结果机制，但入口要按对象性质区分：

- **直接试打**：角色、物品、技能、敌人、敌队、毒、战场，共7个现有页面。
- **带上下文接入**：场景开战、脚本开战、战斗资源及相关全局配置；不能对任意图片/声音/变量无条件给一个“试打”按钮。
- **保留专用验证**：地图、开局、商店、炼蛊皿等世界流程，不能靠一场独立战斗声称验收。

我方配置取自可复用的**我方预设**，敌方/战场由本次试打配置决定；不要求选择开局入口、不加载场景剧情。
从业务页打开时只预填当前对象，其余沿用已选测试配置，避免每次重填。

- 道具边界：content/item.ts:219–261为用途×上下文真源；battle-session.ts:670–686筛选可用和可投掷物品。

## 需要一并覆盖的战斗子功能

不能只接页面按钮却漏掉页面里的难测配置。以下都应使用同一运行核心，但准备条件不相同。

| 子功能 | 模拟器必须能准备的条件 | 应观察的真实结果 |
|---|---|---|
| 普攻、连击、攻击全体、防御、逃跑 | 我方配装、敌方阵形、Boss开关 | 实际行动/目标/伤害/限制，不另算一个预测值代替执行 |
| 普通技能与物品效果链 | 施放者、目标、HP/MP、金钱、背包、技能已用次数 | 合法可选性、消耗、命中/未命中、状态/资源变化 |
| 道具投掷 | 道具数量、投掷者、敌槽、对应表现资源 | 数量扣减、单体/全体目标、真实投掷效果与演出 |
| 装备效果 | 合法穿戴者/槽位、基础值与装备后有效值 | 属性、抗性、授技、常驻状态、全体攻击、回合恢复、战斗外观覆写 |
| 合击与守护 | 满足现行合同的队伍关系、全队状态/血量 | 合击资格/代价/效果、守护触发；不临时篡改公式或角色关系来假装成功 |
| 濒死/阵亡反应 | 队友关系和恰当血量、敌方可触发行动 | 已有伤亡脚本、对话、buff与音效；缺实现仍按Q2缺陷登记 |
| 毒和状态 | 目标阵营、初始毒/状态及剩余回合、抗性 | 玩家/敌人逐回合差异、抵抗、解除、自解、毒关系及耗材 |
| 敌人AI/回合hook | 难度、敌槽、我方能力；能自然运行到所需回合/血量条件 | 条件命中、行动、召唤/分身/变身和游标连续性；复杂条件可后续加受控场景夹具 |
| 偷取与收服 | 对应技能/敌人可偷物和收服值、背包/资源状态 | 获得物、次数/余额变化；已有写回缺陷不能靠结果面板自造数据遮盖 |
| 战场和战斗表现 | 指定战场、我敌双方、真实动作 | 五灵影响、屏波/背景、施法定位、精灵动作和声音同步 |
| 遭遇战斗演出 | 所选startBattle/敌人choreography，必要的真实角色 | 战斗开始/回合开始的对话/音乐/终止指令，仅当前battle子集 |
| 奖励与成长 | 可重建的入战快照、真实结算依赖 | 胜败逃分类、经验/金钱/技能/物品/成长前后差异，仅写临时世界；不写正式存档 |
| 战后事件 | 当前onDefeated子集及所需变量/标志/人物输入 | 隔离世界里的事件与变更轨迹；实际场景剧情连通性仍需场景试玩/E2E |

代码支持不等于无需工程改动：敌方初始毒/状态、特定AI中间态并非所有场景都有现成公共输入。
不足时设计受控的测试输入，不能直接改私有队列/阶段字段冒充真实触发；确定性随机复现也须查全随机源，不能只替换session rng却忽略结算Math.random。

## 统一工作台应具备的配置

建议放在现有“战斗”模块下作为一个工作区（**尚未确定UI形态，不新增一级模块、不已获视觉批准**），
各处“试打/试放”打开同一处并预填对象。原有轻量帧预览、背景预览和音频试听保留，两者解决不同问题。

1. **我方**：选择/保存/复制/重命名/删除我方预设；成员与顺序、等级、基础数值、当前HP/MP、技能、装备。
   基础数值和装备后有效数值分别显示，避免手动填数后装备再加一次。明确“继承角色定义”与“本次覆写”。
2. **敌方**：选择已有敌队，或临时编辑成员/顺序/空槽；可从敌人页只带入单个敌人，不为此创建正式敌队。
   临时属性覆写与正式敌人编辑分开；召唤/变身仍解析工程中真实定义，不能丢掉资源/身份合同。
3. **背包与资源**：测试道具及数量、测试金钱、技能限用计数；支持所需的战斗初始状态。
   技能可能消耗物品/金钱，不是只把MP改大就足够。战外专用物品显示原因，不伪装成战斗可用。
4. **战场**：独立选战场和需要的战斗音乐；场景/脚本入口可带“已解析的有效战场/音乐及来源”，但不要求加载那个场景才能打。
5. **试打与结果**：开始、停止、按相同入战配置重新开始；显示真实结果与消耗/奖励/状态变化。
   首版不必承诺逐帧、时间旅行、批量平衡跑分、录像/完整脚本调试器；它们不是复用入口成立的条件。

### 预设与试打方案分开

- **我方预设**保存可复用的成员、配装、技能和测试资源/覆写；例如“前期低配”“中期常用队”“高等级测试队”。
- **试打方案**组合一个我方预设、敌方、战场及特定测试条件。首版至少应保留本次未启动配置，是否同时持久保存完整试打方案在r2明确，
  不用它拖延用户已明确需要的多套我方预设。
- 每次开始时冻结一份配置副本；扣血、耗蓝、耗物、敌队消耗和战果不会反写预设。只有显式保存预设才改变配置数据。
- 推荐按工程存放编辑器测试配置、随工程备份；不是正常游戏存档，也不是另一套ActorDef。具体目录/版本/是否进入独立可玩包仍需设计，
  必须纳入现有作者保存事务、重开、引用失效提示与安全删除策略，不能随手加localStorage或孤立JSON绕过这些合同。
- 从物品/技能页预填不能无提示覆盖已保存预设；角色/技能/装备被改名或删除后按稳定ID复核，缺失时阻止开始并给定位，绝不回落PAL默认0。

### 等级不能假装等于属性生成

现行instantiate只复制角色baseStats；把level从1改为50不会自动推导50级属性。r2必须明确：
显式等级和基础数值覆写可作为输入；“按成长规则生成指定等级数值”的能力依赖N6b及随机成长口径，不能在模拟器另写第二套升级算法。
同理装备提供的技能、抗性与状态须走正式派生，不能把已派生值永久烙进预设后下一次再叠加。

## 实现边界与成本判断

这已从两个入口bug修复扩大为**中等偏大的编辑器工具功能**；无需重写战斗核心，但不是增加几个按钮。
主要成本在统一输入、保存预设、资源/生命周期隔离、状态准备与真实结果可见性，按钮接线只是最后一层。

| 层 | 应复用 | 需要新做/核实 |
|---|---|---|
| 编辑器配置 | Ds标准表单、当前人物/技能/物品/敌队选择与引用定位 | 统一工作区、来源预填、临时覆写、预设管理 |
| 运行适配 | main现有装备/技能/形象派生、资源readiness、BattleSession | 从私有配置创建临时世界/玩家输入、早分流、共同清理；必要最小提取而非复制main |
| 战斗 | 正式菜单、AI、公式、状态、道具/投掷和演出 | 不另写算法；现有Q2缺陷保持公开，不在模拟器里“修成另一个结果” |
| 结算 | grantBattleRewards、buildSettlementScreens及已有写回规则 | 仅针对临时副本复用、展示结果；模拟器绝不进入正常SaveStore |
| 预设保存 | 作者保存事务/工程身份/重开/引用处理 | 编辑器配置落盘合同、持久化范围与可能的版本影响；旧r1“无需版本升级”不可照搬 |

### 建议按三批接入，不把所有拓展压成一个巨卡

1. **共享底座与主闭环**：完整我方配置/多套预设、敌队、战场、背包与金钱、真实战斗和退出隔离；先替换技能和敌队现有入口。
   基础配置一次按通用模型设计，不先造一个只能试技能的临时方案。需有角色/物品支持数据，但不必所有页面按钮同批接完。
2. **全部直接编辑入口**：角色、物品（装备/使用/投掷）、敌人、毒、战场；补必要初始状态与真实结果观察。
   技能、敌队已在第一批，至此7个D类页面闭合，不遗漏合击/守护/毒/道具等准备条件。
3. **上下文与资源入口**：战斗精灵/背景/头像/音乐/音效、场景敌对和脚本startBattle、战斗演出/战后受控片段、相关项目资源。
   分清battle-only与世界流程，不为接一个页面实现完整X5/D13。各独立接入可按收益再拆小批。

这里只建议分批与边界，**没有决定三批全是E2E前置**。建议原D-04/D-05真实试打与存储隔离必须闭合，
完整工具接入按用户确定的阶段范围推进，不把所有资源按钮/高级条件编辑/长期覆盖率目标变成R4薄E2E的新门槛。
Q2仍负责战斗完整专项测试；模拟器可复用其场景准备，但手动打通一次不替代自动业务断言、概率边界或完整通关。

## r2设计前需要明确的事项

1. 用户确认工作区结构草图、第一批范围；不再询问已被本方向替代的“选开局小弹窗”。
