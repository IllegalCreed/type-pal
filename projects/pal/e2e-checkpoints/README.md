# PAL 全流程 E2E 碎片地图 + 检查点

> **目的**:把整个游戏切成几百个小碎片,每个碎片小到足够独立验证、独立重跑和独立录像。每个碎片 =
> **一个起始检查点**(`NNN-名.save.json`,秒进该状态)+ **一份剧情与执行说明**(本文件每节 + 可选单独 md)
> + **可机器复核的结束条件**。**碎片 N 的结束检查点 = 碎片 N+1 的起始检查点**。这样重复 E2E
> 或重录某个镜头时可从任意碎片直接进入,不必从头通关,也不要求作者手动玩一遍再录屏。
>
> 碎片边界由作者(仙剑专家)最终确认。Agent 可以根据
> [`docs/lore/timeline.md`](../../../docs/lore/timeline.md)、场景/脚本数据和既有验证证据起草候选边界,
> 但**不得把猜测直接登记成剧情真值**。作者只需审核边界和内容语义,不承担手动通关、录屏或给无标签录像补剧情说明。

## 1. 产品定位与前置关系

全流程 E2E 同时服务三个目标,但三者必须共用同一份碎片真值:

1. **回归验证**:证明剧情、演出、场景切换、存读档和结局可从头到尾走通。
2. **视觉抽验**:从任意剧情点恢复,只检查本段需要人工判断的画面、节拍和观感。
3. **自动化录像**:把已知剧情语义、起止状态和关键画面交给受控录制器,逐段生成可检索素材。

自动录像是 E2E 的下游消费者。没有完整碎片目录、确定性操作、状态断言和剧情语义时,不得把一条
长录像或一批无标签 clip 冒充可用素材。视频脚本可以提前讨论,但 Content Studio 的分镜录制和制作任务
必须保持阻塞,直到对应碎片达到本文的 `capture-ready` 门槛。

```text
剧情时间线
  → E2E 碎片目录
    → 起始检查点 + 确定性操作 + 状态断言
      → 剧情语义 + 可录制时刻
        → Content Studio 分镜映射
          → 分段录像
            → 合成 / 字幕 / 配音 / 封面
```

## 2. 第一阶段与第二阶段的边界

两阶段可以共享**剧情碎片的语义身份**,不能共享引擎内部真值或存档格式:

| 范围 | E2E 目标 | 真值与约束 |
|---|---|---|
| 第一阶段 `@type-pal/game` | 证明忠实还原运行时从新游戏到结局可完整游玩,并覆盖桃源村等支线与生产增强工具 | 原版 / 一阶段规则为行为真值;按第一阶段测试纪律核对 |
| 第二阶段 `@type-pal/reforge` + `projects/pal` | 证明迁移后的 PAL 内容能在新引擎完整运行,剧情内容和目标观感成立 | 第一阶段只作 UX 与内容参考;不要求内部状态、逐格走位或旧引擎怪癖一致 |
| 第二阶段 `@type-pal/editor` | 证明创作者能创建/打开工程,编辑内容,保存重开并进入试玩 | 以 Reforge 干净架构和当前 canonical schema 为真值;不是复刻旧编辑方式 |

- 同一个剧情段可以有稳定的跨阶段语义名,但每个阶段拥有独立 checkpoint、输入脚本和断言。
- 第二阶段 checkpoint 只消费当前 canonical 版本。schema/save 切换后应从上游重新生成,不得为了保留旧
  E2E 存档而增加 upgrader、fallback 或双读双写。
- 编辑器 E2E 是创作工作流图,不是主线剧情的线性续段;它与 Reforge 试玩通过稳定工程状态和试玩入口关联。

> **版本切换顺序（用户，2026-09-05，取代 2026-09-03 的具体版本号）**：SceneIndex 先原子切 content20；
> 再在 content20 上完成 Q1 runner + 001-010 薄基线、四种取物运行态 canary 和一条
> “编辑→保存→重开→试玩”工作流；随后 N6b 原子切 content21 并重生成当前工程，
> 用同一业务断言复跑通过后才扩完整 Q1/Q2。版本绑定 checkpoint 与 raw JSON fixture 必须重建，但
> fragmentId、操作契约及剧情/库存/实体生命周期/战斗结果断言应跨版本保持有效。

> **开工前置（用户，2026-09-05）**：完成商店生命周期闭环后，先开展第一、第二阶段全仓代码审计并
> 处理影响数据安全、流程正确性和 E2E 可信度的阻断问题，再开始 R4；一般优化不要求在 E2E 前全部完成。

## 3. 碎片必须携带的剧情语义

碎片不能只有序号和一串按键。每段在进入实现前至少要明确下列信息;具体文件格式和 schema 另开设计任务
评审,本文先冻结语义要求:

- **稳定身份**:`fragmentId`、阶段、章节、标题和种类(`main-story` / `side-story` / `battle-showcase` /
  `tool-workflow` / `editor-workflow`)。
- **剧情上下文**:本段发生了什么、为何发生、承接哪一段、结束后改变了什么。
- **画面语义**:地点、场景 ID / 地图名、出场角色、关键物品、Boss、音乐或过场。
- **起始契约**:checkpoint、目标场景、队伍/世界状态和可观察前置条件。
- **操作契约**:确定性键盘/编辑器操作、等待条件、允许的测试辅助和禁止跳过的事件。
- **验证契约**:应出现的对话、演出、战斗、状态变化、奖励和失败信号。
- **结束契约**:机器可观察的结束条件、结束状态摘要和下一碎片 checkpoint。
- **录像语义**:值得录制的起止事件、画面意图、建议时长、是否需要真实战斗、是否包含剧透及内容标签。

Type Pal 只拥有上述项目事实和稳定 `fragmentId`。Content Studio 拥有 `activityId`、分镜、clip 和成品版本;
不得把某次宣传活动的业务 ID 写回 Type Pal 剧情真值。两者通过显式映射关联,避免 E2E 被某一轮宣传计划绑死。

## 4. 验证档与录像档

同一碎片允许两种执行 profile。它们共享起始状态、剧情语义和结束契约,但中间操作可以针对目标收窄:

| Profile | 目的 | 战斗与等待 | 输出 |
|---|---|---|---|
| `verify` | 快速证明流程/演出和状态转换正确 | 非战斗专题可用 `?win` 速胜并跳过无意义等待;仍须运行所有会改变剧情状态的事件 | 断言、结束 checkpoint、执行回执,可选抽验截图 |
| `capture` | 生成可直接进入视频制作的真实素材 | 精选战斗用固定 RNG / 预设策略走真实回合;演出按正常节拍播放,不显示 debug UI,不得用突兀速胜破坏镜头 | 带 `fragmentId` 和剧情标签的独立 clip、关键帧与录制回执 |

- `?win` 不是所有 E2E 的全局规则,只允许用于不以战斗表现为目标的 `verify` 执行。
- `capture` 与 `verify` 最终必须落到等价的剧情结束契约;若录像档会改变剧情结果,应拆成另一个碎片。
- 随机战斗、掉落、暴击和敌方决策必须提供可重复 seed 或预设输入,不能靠“多录几次总会成功”。
- 录像失败只重跑当前碎片。不得因为一个镜头错误而从新游戏重新通关或重录整期视频。

> **阶段与顺序裁决（用户，2026-09-03）**：`capture` profile、Content Studio 窄录制适配和分镜映射
> 属于第二阶段发布工作，但严格依赖 Q1/Q2 的 `verify`、checkpoint 链和执行回执。先完成 E2E，再接录像；
> 不得反过来用录像成功推断流程或战斗正确。

## 5. 检查点链与执行回执

主线碎片从唯一干净新游戏入口顺序生成 checkpoint。常规回归和录像从已生成的任意 checkpoint 恢复;
schema、迁移结果或相关内容变化后,整条受影响链从最近仍可信的上游重新生成。

每次执行至少产出以下可追溯信息:

- `fragmentId`、阶段、执行 profile、项目 commit / 内容版本和运行环境。
- 输入 checkpoint 的版本与摘要,以及结束状态 / 输出 checkpoint 的摘要。
- 每个验证点的通过、失败或未执行状态,首个失败原因和最后可信状态。
- 实际观察到的场景、角色、剧情事件与预期的差异。
- 生成的截图、clip 或日志的窄路径与内容哈希;不保存凭据或浏览器 profile。
- 是否达到 `verified`、`visually-sampled` 或 `capture-ready`,以及仍缺哪个门槛。

执行回执是后续录制和 Content Studio 进度投影的事实来源;“脚本跑完且进程退出 0”不能替代逐段回执。

## 6. 覆盖模型

“玩通游戏”是有分支的剧情图,不是一条巨型 Playwright 脚本。完整覆盖至少包括:

### 第一阶段游戏

- 新游戏、主线各章、最终战、结局视频和回标题。
- 桃源村等有进入时限或可错过的大型支线。
- 代表性的普通战、Boss 战、剧情必败战和战斗后续演出。
- 小地图、战斗辅助信息、历史对话、计时器、快捷存读档、存档导入导出、显示/音频/FPS 和离线能力。
- 计划中的每一期宣传活动都至少有一组已验证且带语义的候选碎片,但 E2E 本身不依赖活动存在。

### 第二阶段 Reforge 游戏

- 从开场到结局的迁移 PAL 内容主链、支线和代表战斗。
- 标题/入口、场景呈现、菜单、存读档、试玩跳转和结局返回等跨系统闭环。
- 对第一阶段已打磨 UX 的定向抽验;只比较用户可见目标,不把旧内部机制带进新引擎。

### 第二阶段编辑器

- 新建空白工程、打开/克隆工程、保存/另存、关闭重开。
- 场景、地图、剧情、角色、物品、战斗、资源和工程等核心创作工作流。
- 编辑 → 保存 → 重开 → 试玩 → 返回编辑器的闭环,并证明试玩读取的是刚保存的当前工程。
- 原生目录授权等必须人工介入的系统边界单独登记,不能伪装成无人值守自动化成功。

## 7. 自动录像与 Content Studio 接口边界

E2E 完整不自动授予录制器任意控制权。进入 Content Studio 自动录像前还必须:

1. 用 Chrome 对真实页面完成 DOM-first 调研,覆盖启动、加载、对话、菜单、战斗、工具面板、编辑器、
   文件选择和异步弹窗等会进入镜头或控制流的状态。
2. 为每个需要操作或观察的元素建立经过独立验证的 role / label / text / test-id 清单;游戏画布只通过
   项目已定义的键盘输入和机读状态交互,不得依赖坐标点击或任意选择器。
3. 将项目 E2E / 录制能力注册为项目负责人批准的窄适配器。MCP 和活动数据只引用已登记的 `fragmentId`
   与允许的录制 profile,不接收任意 Playwright、Shell 或选择器。
4. 录制器按 `precondition → 一个语义动作 → postcondition` 执行;未知弹窗、定位数量变化或剧情状态漂移
   立即停止并返回 DOM / E2E 调研,不得猜着继续。
5. 原始录像、合成、字幕、配音和封面由 Content Studio 保存在其窄产物目录并记录版本;不提交到 Type Pal
   源码仓库,也不反向修改剧情真值。

作者在这条链中的必要动作是审核剧情碎片边界、宣传脚本和最终成品,不是手动通关录屏或替 Agent 给无标签
素材补剧情信息。

## 8. 自动录像准入门槛

只有同时满足以下条件,对应范围才可标记 `capture-ready`:

- [ ] 碎片边界和剧情语义已由作者确认。
- [ ] 起始 checkpoint 可从 canonical 内容重建,结束 checkpoint 可重复生成。
- [ ] `verify` 从起始状态稳定到达结束契约,关键状态断言齐全。
- [ ] 需要展示的战斗/演出有独立 `capture` 路径,且正常节拍下可重复。
- [ ] 主线、支线、辅助功能或编辑器工作流的覆盖缺口已登记,没有用单条 happy path 冒充全覆盖。
- [ ] 每段执行回执能唯一关联 `fragmentId`、输入、输出、版本和证据。
- [ ] Chrome DOM 清单与窄录制适配器已经审查,没有坐标、任意选择器或未知状态兜底。
- [ ] Content Studio 分镜显式映射到已验证碎片,失败时只重录当前 clip。

第一阶段和第二阶段各自达到完整范围的 E2E 门槛后,才解除对应系列视频的自动录像阻塞。不得因已有几段
可录画面就把未覆盖范围标成“自动化已打通”。

## 9. 已有机制与待建项

- **Reforge 存档恢复**:`?e2e-load=<save.json url>&e2e-load-scene=<id>` 复用正式读档归一化与恢复事务,
  注入 world 并跳到碎片起点。
- **机读观察点**:`canvas.dataset.rfScene` / `rfRender` / `rfSceneEntry`、`window.__reforge` 和战斗态
